A mission outlives every process

A prompt becomes a mission with frozen acceptance criteria. A systemd daemon polls the mission ledger every 300 s and keeps each mission moving — across reboots, crashes, and session teardown — until the criteria are met.

Architecture

The daemon owns the loop, not the run

Deliver runs already survive their tool call, but nothing resumed them after a reboot or relaunched them after a crash. The mission layer fixes that: the ledger holds the goal, the poll daemon decides, and the deliver run does the work.

■ pid gone

Mark interrupted, relaunch

A crash that never marked itself. The state file says running; the pid says otherwise.

▲ terminal

Salvage, then resume

First relaunch is immediate. Repeated failures wait: 15, 30, 60 min…

● delivered

Close the mission

The run converged against the real gates. The mission is done.

Backoff

First resume is immediate; repeats double

A clean interruption is the healthy case, not a crash loop, so the first relaunch happens at once. Only repeated failures back off — the same lesson as the systemd start-rate limiter: back off, do not hammer.

Struggle & salvage

The orchestrator proposes; the overseer rules

Every failed attempt seeds a salvage proposal: what happened, what partial work exists, what to try next. Nothing schedules until a human — or an overseer agent — approves.

▲ struggling

Past 3 failures on one task, the proposal turns into an escalation ask — posted to the collaboration board, still approval-gated: uap mission salvage approve <id>.

Frozen acceptance

"Complete" means the hash matches

Acceptance criteria are hashed at creation. The criteria travel inside every run instruction, so the acceptance judge grades the frozen text — not a paraphrase. Change requires an explicit replan that records the prior text, hash, and reason.
